## The task — three defects, each with its assertion

### Defect 1 — a concurrent issue can burn an invoice number (audit F2)

`issue_invoice` reads the invoice with a plain `select * into v_invoice from invoices where id = v_invoice_id` (`supabase/migrations/0108_issue_invoice_rpc.sql:58`), checks `status = 'Draft' and invoice_no is null` (`:67-71`), then mints (`:79`) and updates (`:106-113`). Two concurrent callers both pass the check; both mint; the second update wins the row and the first number is consumed and never used. A gap in `INV-` is exactly what `0086_invoice_write_rights_and_draft_without_number.sql:88-91` says must never happen.

1. Lock the row: `select … into v_invoice from invoices where id = v_invoice_id for update`, and re-check Draft + `invoice_no is null` **under that lock** before minting.
2. Make `invoice_no` un-rewritable on an issued row. `reject_invoice_edit_after_issue` (`0006_finance.sql:487-531`) protects seven money columns but **not** `invoice_no` or `issue_date`. Add them to the guard (a fresh `before update` trigger in this migration is acceptable if you prefer not to touch 0006's function body — say which you chose and why).
3. Effect on the loser: a named, catchable refusal (`P0001`-style message), never a silent success and never a second number.

**Assertion (lifecycle):** two sessions settle the same Draft through `issue_invoice`; exactly one succeeds, the other gets a named refusal, `invoices` holds exactly one number, and `number_sequences.current_value` advanced by exactly **1**.

### Defect 2 — an issued invoice's lines can be rewritten while its total stays put (audit F5)

The header is protected; the lines are not. The only trigger on `invoice_lines` is `trg_recalc_invoice_lines` (`0010_triggers_functions.sql:200`), and `recalculate_invoice_totals` sums the **stored** `line_total` (`0098_invoice_totals_match_engine.sql:431-434`). So `update invoice_lines set unit_rate = …` (or `description`, or `quantity`) on an **issued** invoice changes the document and leaves the sum — and therefore every header column — identical, so nothing raises. RLS permits it for Owner/Admin/Manager/Accounts (`0086:133-157`).

1. Add a `before insert or update or delete on invoice_lines` guard that raises unless the parent invoice's `status = 'Draft'` and `voided_at is null`. No DELETE policy exists today (Law 3, `0086:130-131`) — the guard is a backstop, not a replacement.
2. The message must name the invoice and say what to do instead: *"an issued invoice's lines are immutable — correct it with a credit note."*

**Assertion (lifecycle):** after issue, `update invoice_lines set unit_rate = … where invoice_id = <issued>` raises; the same update on a `Draft` parent succeeds and the header recomputes.

### Defect 3 — an extension does not reprice the draft, and two files claim it does (audit F4)

`0111_extend_booking_rpc.sql:126-129` increments `invoice_lines.days` on Draft invoices and the migration header (`:9`) plus `src/actions/rentals/extendRental.ts:16` both say `recalculate_invoice_totals` then reprices it. It does not: `line_total` is a stored column (`0006_finance.sql:152`, no `GENERATED` anywhere) and the recalc only sums it. The client is quoted the old price for the extra days.

1. In `extend_booking`, recompute `line_total` for the affected Draft lines from the same arithmetic `create_invoice` already uses (`0168_booking_line_totals_and_breakdown.sql:871`: `qty × days × rate − discount`), or call a single shared helper that does. Do **not** re-implement pricing in TypeScript — the SQL derivation is the one that bills.
2. Crew lines are per-engagement totals, not per-day (`0168:887-895`); an extension must not silently multiply accommodation or meals. State explicitly in the migration what happens to crew lines and why.
3. Correct the two false claims if your fix does not make them true.

**Assertion (lifecycle):** draft → `extend_booking` +2 days → `invoice_lines.days`, `invoice_lines.line_total`, `invoices.subtotal` and `invoices.total_amount` all move by the amount the engine computes for those two days; a **issued** invoice's lines are untouched by the same call.
