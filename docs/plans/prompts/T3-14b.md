## The task

### 1. One re-sync function, one owner

Add `resync_draft_invoice(p_booking_id uuid)` (name it as you like, keep it one function) that re-derives the Draft's lines from the booking and rewrites them **only while the invoice is `Draft`**:

- Equipment lines from `booking_lines` (`voided_at is null`), crew from `booking_crew_lines`, transport from `booking_transport`, discounts from the booking's discount rows — the same sources and the same arithmetic as `create_invoice` (`0168:848-877`, `:896-912`, and the discount/transport blocks around them).
- **No DELETE.** `invoice_lines` has no DELETE policy by design (`0086_invoice_write_rights_and_draft_without_number.sql:130-131`, Law 3), and `invoice_lines.client_uuid` is `UNIQUE`, reused from the source row. So re-sync is an **upsert keyed by the source row's `client_uuid`**: insert lines for new source rows, update lines for changed ones, and zero-contribution lines whose source row was voided (keep the row, keep its history) rather than deleting them. If that leaves a line with `quantity`/`days` below their `CHECK` floors, state how you handle it — do not silently drop the row.
- Recompute `line_total` on every written line, so `recalculate_invoice_totals` has a truthful sum to total.
- Refuse (named error) when the invoice is not `Draft`, or when the booking is cancelled.

Call it from `extend_booking` instead of the day-only update at `0111_extend_booking_rpc.sql:126-129` if T3-14a did not already do so, and from every other post-Confirm booking mutation that T3-18 owns (line add/remove, date change, discount, crew, delivery, late fee in `0163`-era code — trace the actual RPCs, do not assume).

**Assertion (lifecycle):** extend by 2 days → `invoice_lines.days`, `line_total`, `invoices.subtotal` and `total_amount` all move by the engine's amount; add a line → the Draft gains exactly one line; void a booking line → the Draft's matching line stops counting toward the total but still exists; a **non-Draft** invoice is never touched.

### 2. Draft at Confirm

1. Draft creation happens **inside the confirm transaction** — same commit, same failure. If the draft cannot be created, Confirm fails and says why; it must never report a confirmed booking with no invoice.
2. Law 8 key: derive it **deterministically from the booking** (the booking id, or a uuid5 of it) so a second Confirm press replays rather than creating a second invoice. The existing `create_invoice` already refuses a second invoice for a booking including a voided one (`0168:751-756`) — that is the backstop, not the plan.
3. Keep the existing offline refusal exactly as it is (`src/actions/rentals/confirmRental.ts:415-420`). Confirm is not queued offline.
4. Keep the stage read-back (`confirmRental.ts:567` + the read after it). The draft is an additional effect of Confirm, not a replacement for the transition.
5. Bookings with no advance: keep today's behaviour (a quote holds no gear; staff may Confirm and see the "advance not paid" soft gate, W82/W86). Do not add a new hard gate.

**Assertion (lifecycle):** Confirm as Coordinator → exactly one invoice, `status='Draft'`, `invoice_no IS NULL`, `issue_date IS NULL`, line count equals the billable booking lines, one audit row. Confirm twice with the same key → still one invoice. A genuine second intent → named refusal.
