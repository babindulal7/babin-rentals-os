# Cadra requirement evidence

This maps the original handoff's R-01–R-20 acceptance scenarios to the implemented local checks. It is an evidence index, not an independent PASS receipt. Current execution counts, source fingerprints and failures belong to [interaction and gate results](CADRA_INTERACTION_RESULTS.md) and the [before/after matrix](CADRA_BEFORE_AFTER_VISUAL_MATRIX.md). A test file's presence alone does not establish that the final source passed it. Historical full-suite receipts do not certify subsequent source changes.

The route matrix uses a seeded mock Owner and anonymous auth screens. It cannot establish money-blind role behavior, actual hosted access or every action's successful persistence. Vitest assertions, local Postgres contracts, browser geometry and physical-device acceptance have different scopes and remain identified below.

## Money DOM and payload evidence

These checks are complementary. They do not substitute for a hosted payload audit.

- **Money-visible versus money-blind DOM:** `src/__tests__/e2e/tier3-cross-feature.test.tsx` mounts Rentals for Owner and Warehouse, asserting the Total Amount column/figure is present for Owner and omitted for Warehouse. `src/modules/operations/__tests__/QuickOperationsPopUp.test.tsx` asserts no currency/rate text in Warehouse Operations. `src/modules/finance/__tests__/Finance.restricted.test.tsx` asserts Warehouse restricted DOM and that its four known-denied finance requests are not sent. `src/modules/reports/__tests__/Reports.law16.states.test.tsx` asserts no Client Report money request and no Rental Report rupee figure for a money-blind role.
- **Requested columns and parsed values:** `src/lib/queries/__tests__/inventory.test.ts` inspects default money-free selects, explicit money selection and masked null handling. `src/lib/queries/__tests__/finance.test.ts` checks the five money-visible roles against Warehouse/Technician/Driver/Client and revoked column omissions. `src/actions/inventory/__tests__/updateEquipmentUnit.test.ts` strips unexpected money from the confirmed action snapshot.
- **Actual local SQL payloads and grants:** `scripts/test-calendar-planning.mjs` inspects both Owner and Warehouse `calendar_resource_window()` JSON for forbidden rate/price/amount fields. `scripts/check-astra-phase0.mjs` SEC-02 loops all nine roles, denying internal estimate access to every API role and price/document-location helpers to the four money-blind roles. These run against disposable local Postgres with simulated authentication context, not hosted JWT/PostgREST.
- **Remaining boundary:** the named DOM cases directly cover Owner/Warehouse and selected report states. They do not establish a complete rendered-app and network sweep for Technician and Driver. Keep this distinction when reporting the final suite/security results.

## Supported modes and motion

`src/lib/theme.tsx` declares `system`, `dark`, `light`, **`high-contrast`**, `glass` and `glass-light`. High contrast is an explicit resolved theme with its own `:root[data-theme='high-contrast']` palette; it is not the inactive black/light, Luma or Rhea preset. Glass modes combine a dark/light base with `data-style='glass'`. `Header.tsx` exposes the modes.

`scripts/check-contrast.cjs` covers selected high-contrast pairs and composites translucent glass cards over the glow/canvas before checking the worst tested background. Describe that receipt as selected shipped-token/composed-surface contrast coverage, without extrapolating to a full browser accessibility pass.

Both the matrix and interaction driver request `reducedMotion: 'reduce'`. The current interaction receipt also executes computed assertions: forced colors yields a solid 2px active-navigation outline, and a probe requesting animation/transition computes `animation:none` and `transition:0s`. Loaded Today boards are checked in high contrast, dark/light glass and system-dark at desktop/phone sizes, including actual selected-navigation contrast. These named assertions do not establish reduced-transparency, native zoom, physical-device or screen-reader acceptance.

## Modal and secondary-state coverage

The route/query matrix and named Operations/unit/Calendar/browser interactions have different scope. Operations component suites cover stage opening, real blockers, dirty/discard and failed reads; record suites cover create/edit validation, retries and section saves; chart suites cover real tooltip dismissal. The browser driver inspects the actual Return modal, navigation overlays, unit editor reflow and schedule-amendment generation. This is not a claim that every application's dialog has been independently driven through a successful save. Keep any unsampled modal, unsupported action and physical-device check explicitly separate from route geometry acceptance.
