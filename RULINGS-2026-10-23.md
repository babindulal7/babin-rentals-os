# Rulings — 23 October 2026

## P0-B second half: operations grants are branch-scoped (migration 0171)

OPEN_DECISIONS (20 Oct 2026) held location scoping as the open half of P0-B: "a grant is
meaningless without a site." Resolved locally — **WRITTEN + VERIFIED (check:pglite 169/169 +
check:lifecycle 31/31, same run), NOT APPLIED** (N-5: Babin applies after `BACKUP_PROTOCOL.md`).

Three design decisions, all in the migration header and enforced by
`scripts/test-operations-grants.mjs` (32/32):

| # | Ruling | Why | Changed where | Revert |
|---|---|---|---|---|
| 1 | **Branch is the site, and grants are NARROWING-ONLY.** A staff member with no `operations_grants` rows — active or revoked — keeps today's role-based permission at every branch. Grant rows only remove branches, never add roles. | `bookings.branch_id` has been NOT NULL since 0002 and `users.branch_id` since 0007 — the branch is the org's operational unit and the rental's site. Narrowing-only makes the migration deploy-safe: applying it changes nothing until an admin opts a user into scoping by issuing their first grant. | `0171_operations_branch_grants.sql` (`auth_may_perform_operation`); `rbac.ts` docblock already stated "may this role at this site is the DB's job" — unchanged, now true | drop table + functions |
| 2 | **Revoke means scoped-to-nothing, never back-to-global.** The helper is three-state: pristine (no rows) = legacy global; any grant history = scoped, and then only an ACTIVE grant for the booking's branch passes. | Without the third state, revoking someone's last grant would silently re-widen them to every branch — the opposite of the admin's intent. Re-issue after revoke re-grants (partial unique index covers active rows only). Law 3: revoke is a state (`revoked_at`/`revoked_by`), never a delete. | same | restore the two-branch helper body |
| 3 | **The gate lives fail-closed where custody moves.** `apply_booking_stage_transition()` (re-created from 0155 with exactly the gate insertions) refuses Booked→Packed / Packed→On Rent / On Rent→Returned on an ungranted branch **before** any session check; `assert_operation_branch_grant()` is the early truthful refusal `runFloorVerb` calls (step 1b) for all four verbs — and Reset's ONLY branch gate, since Reset changes no stage and has no session. | R-40's own principle: custody transitions are fail-closed DB RPCs. A cross-branch transition is refused even if the application forgot to ask. Reset's assert is client-initiated — the same trust level as today's client-side role checks; stated openly, not hidden. | `0171` (trigger + assert RPC); `floorVerb.ts` step 1b (skipped in mock mode, which has no DB gates at all) | delete the three gate blocks + the step-1b call |

Also ruled, in passing:

- **Issue/revoke are Owner · Admin only** (`issue_operations_grant` / `revoke_operations_grant`, both
  Law 8-idempotent, both audited by the table's own immutable `granted_by/at` + `revoked_by/at` —
  `audit_events.action` is an enum, and 0155's CloseOverride lesson is not repeated). Babin may widen
  this set by one line in the role gate.
- **RLS:** staff read their own grants; Owner/Admin/Manager read all; writes are RPC-only —
  `INSERT/UPDATE/DELETE` privileges are revoked from authenticated outright (defense in depth:
  the prelude's default privileges would otherwise leave RLS as the only barrier).
- **Grants are not money and carry no money fields** — Law 6 untouched.

**Known follow-ups (not built):**

- A grant-issuance UI (Settings ▸ Staff). Until it exists, grants are issued by Owner/Admin via the
  two RPCs (psql/SQL console). The RPCs are the complete, tested surface; the UI is presentation.
- The Technician-excluded-from-Handover cell remains Babin's open TODO(decision) in OPEN_DECISIONS —
  this ruling does not touch the role matrix.
- Revert for the whole feature: `drop table operations_grants`, drop the four functions, restore the
  0155 body of `apply_booking_stage_transition` (the three gate blocks are the only edit), remove
  `floorVerb.ts` step 1b and the `GRANT_SLUG` map.
