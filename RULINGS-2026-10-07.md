# Rulings — 7 Oct 2026

## R-07-01 — Promo codes come from the `coupons` table only
Source: Booqable scrape adoption spec §3.
`PROMO_CODES` in `src/lib/pricingPipeline.ts` (NEPALFILM, MONSOON26, KATHMANDU, KATHMANDU10,
FILMSTUDENT) was demo data validated on the production New Rental path. Removed.
`src/lib/queries/promoLookup.ts` now reads `coupons` (code, % , min booking, validity,
redemption cap, is_active). A failed read says "could not verify"; it never invents a discount.
Revert = restore the constant from 06c0dcf.
Known limit: `coupons_select` RLS is `auth_can_view_money()` (0037), so a money-blind role gets
"could not verify" at booking. TODO(decision): a narrow read for active coupons, or leave coupon
entry to money-visible roles.

## R-07-02 — Only money-visible roles enter a coupon code (Babin, 7 Oct)
Resolves the R-07-01 TODO. The coupon field is shown only where `canViewMoney` is true
(`RentalFinancialRail` already returns null otherwise; `RentalPricingSection` now gates it).
The `coupons_select` RLS (0037) is therefore left as is. No narrow read added.

## R-07-05 — G1 settings table (0158): Owner writes, money keys are money-gated, location override only for the day cut
- Write = **Owner only**. The spec said Owner/Admin; `PERMISSIONS.md` §4.10 says the code is Owner only (`canManageSettings`). Stricter wins (B-1).
- Read = any staff, except the Financial keys (`settings_key_is_money`), which need `auth_can_view_money()` (Law 6).
- Resolution: location → org → coded default (R-07-03). History is database-written and append-only.
- `DEVICE_KEYS` = `density`, `language` stay in localStorage. TODO(decision): `language` per device is my reading, not a ruling.
- Existing per-device values are NOT copied up to the table. Until an Owner saves, a shared key reads the coded default. TODO(decision): one-time import from the Owner's device?
- Numbered 0158 because 0157 is on `step1-foundation`. Revert = drop `settings_history`, `settings`, `settings_key_is_money`.
